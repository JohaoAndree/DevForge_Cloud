# Walkthrough ADR-003: componente de entorno y balanceo de carga

DevForge Cloud ya declara la topología completa de cada entorno mediante una abstracción reutilizable. La [decisión del ADR-003](../adrs/ADR-003.md#4-decisión) adopta `DevForgeEnvironment`, un `ComponentResource` que reúne red, persistencia, aplicaciones y balanceador. Así, `dev` y `prod` se construyen con el mismo código y se diferencian por el contrato de configuración de ADR-002. Nginx recibe sus destinos desde ese contrato, sin montar el socket de Docker para descubrir contenedores.

El flujo comienza en [__main__.py](../../__main__.py): `orchestrate_infrastructure()` carga y valida el `EnvironmentConfig` e instancia el componente. En [environment_stack.py](../../components/environment_stack.py), todos los recursos se declaran con `parent=self`, incluida la red creada por `create_isolated_network()`. Esta relación los agrupa bajo el entorno en el grafo de Pulumi. El balanceador también declara `depends_on` sobre las réplicas, expresando su dependencia de esos recursos.

PostgreSQL monta un volumen propio del stack en `/var/lib/postgresql/data` y declara `ports=[]`. Las réplicas de `traefik/whoami` también quedan sin puertos publicados al host; el acceso HTTP se concentra en Nginx. PgAdmin se incorpora cuando `enable_pgadmin` está habilitado, y la validación heredada de ADR-002 impide habilitarlo para `environment="prod"`. Con los YAML actuales, las entradas declaradas son:

| Stack | Réplicas | URL del servicio | URL de PgAdmin |
| :--- | :--- | :--- | :--- |
| `dev` | 1 | `http://localhost:8080` | `http://localhost:5050` |
| `prod` | 3 | `http://localhost:80` | No se declara |

El balanceo se prepara en [load_balancer_conf.py](../../components/load_balancer_conf.py). `build_upstream_hosts()` construye una tupla ordenada con los nombres de las réplicas y su puerto interno. `render_nginx_load_balancer_conf()` convierte esos destinos en un bloque `upstream devforge_backend`; para `prod`, su contenido es:

```nginx
upstream devforge_backend {
    server devforge-prod-app-1:80;
    server devforge-prod-app-2:80;
    server devforge-prod-app-3:80;
}
```

La configuración completa añade un servidor en el puerto interno `80`, dirige `location /` hacia ese upstream y pasa las cabeceras `Host` y `X-Forwarded-For`. El componente la genera en memoria y la entrega mediante `ContainerUploadArgs` en `/etc/nginx/nginx.conf`. El esquema Round-Robin elegido en el ADR queda expresado por esa lista de destinos; cambiar `replicas` modifica tanto los contenedores declarados como la configuración entregada a Nginx en la siguiente evaluación del programa.

El componente marca la contraseña recibida como `pulumi.Output.secret` y la utiliza en las variables de PostgreSQL y PgAdmin. Según el contrato aprobado, si no recibe una contraseña utiliza un valor predeterminado derivado del stack. El orquestador actual usa ese valor predeterminado, también para `prod`: marcarlo como secreto no elimina su carácter predecible. Los outputs publicados permiten consultar la configuración, la red, las URLs y los destinos del balanceador, conservando los metadatos de ADR-001.

Las [pruebas del componente](../../tests/test_environment_stack.py) verifican el orden de los destinos, el rechazo de entradas inválidas, la jerarquía de los recursos y las topologías de ambos entornos, incluidos puertos, volumen, configuración inyectada y propagación del secreto de PostgreSQL. La revisión obtuvo `25 passed` para las tres suites con `venv\Scripts\python -m pytest` y compilación correcta con `venv\Scripts\python -m compileall -q .`. Los mocks validan el grafo declarado; el reparto HTTP real, la recuperación ante fallos y los tiempos de despliegue requieren una comprobación posterior con Docker.
