# Walkthrough ADR-002: configuración y redes por entorno

DevForge Cloud ya define una configuración y una red Docker propias para cada stack. La [decisión del ADR-002](../adrs/ADR-002.md#4-decisión) adopta Docker local y Pulumi Stacks para preparar entornos `dev` y `prod` en una misma estación, con nombres y puertos diferenciados y sin depender de una cuenta cloud para el MVP. Esta implementación establece el contrato y la red sobre los que ADR-003 incorporará los contenedores y el componente reutilizable.

[Pulumi.dev.yaml](../../Pulumi.dev.yaml) declara una réplica, puerto de balanceador `8080` y PgAdmin habilitado; [Pulumi.prod.yaml](../../Pulumi.prod.yaml) declara tres réplicas, puerto `80` y PgAdmin deshabilitado. Ambos archivos contienen únicamente los parámetros previstos, sin contraseñas. Las réplicas y los puertos quedan preparados para los servicios futuros: el recurso definido en esta etapa es la red.

El flujo comienza en [config_loader.py](../../components/config_loader.py). `load_environment_config()` consulta la configuración activa mediante `pulumi.Config("devforge-cloud")`, obtiene el nombre del stack y devuelve un `EnvironmentConfig` tipado e inmutable. Antes de construirlo, rechaza réplicas menores que uno, puertos fuera de `1..65535`, puertos de balanceador y PgAdmin iguales, y PgAdmin habilitado cuando `environment` es `prod`. Así, una configuración inválida detiene la orquestación antes de declarar la red. `to_export_dict()` produce un diccionario nuevo para publicar el contrato sin alterar el objeto original.

[network_factory.py](../../components/network_factory.py) recibe ese contrato y declara un `pulumi_docker.Network` con driver `bridge`. Su nombre lógico identifica el recurso en Pulumi y su nombre físico identifica la red en Docker; ambos incorporan el stack. Para los dos entornos previstos, el resultado es:

| Stack | Nombre lógico en Pulumi | Nombre físico en Docker |
| :--- | :--- | :--- |
| `dev` | `devforge-dev-network` | `devforge-dev-net` |
| `prod` | `devforge-prod-network` | `devforge-prod-net` |

En [__main__.py](../../__main__.py), `orchestrate_infrastructure()` conecta la carga del contrato con la creación de la red y exporta `environment_config` y `network_name`. El módulo conserva el output `metadata` de ADR-001 y activa la orquestación cuando existe la clave `environment`; esto permite seguir verificando los metadatos sin configurar un entorno completo. El grafo se expresa mediante recursos Pulumi, sin llamadas directas al daemon ni scripts imperativos de creación de redes.

Las [pruebas de aislamiento](../../tests/test_stack_isolation.py) verifican ambos YAML, la inmutabilidad del contrato, sus validaciones, los nombres y el driver de las redes, y los outputs del orquestador. Junto con las pruebas de ADR-001, la revisión obtuvo `16 passed` con `venv\Scripts\python -m pytest` y compilación correcta con `venv\Scripts\python -m compileall -q .`. Los mocks validan las propiedades declaradas del grafo; el despliegue real, la conectividad entre contenedores y la operación del backend local quedan fuera de esa comprobación.
