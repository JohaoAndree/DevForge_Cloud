# ADR-001: Elección de Pulumi con Python como Motor y Lenguaje de Infraestructura como Código (IaC)

## PARTE A — DECISIÓN (congelada al aceptar)

### 1. Contexto
El proyecto *DevForge v1.0* utilizaba scripts imperativos en PowerShell (`winget`) para aprovisionar entornos de desarrollo locales en Windows. Este enfoque carece de un motor de gestión de estado (*State Management*), no garantiza idempotencia ante fallos parciales y contamina el sistema operativo anfitrión. Para evolucionar hacia *DevForge Cloud*, se requiere seleccionar una herramienta de Infraestructura como Código (IaC) que permita definir redes, contenedores, volúmenes y balanceadores de carga de forma declarativa, calcule un grafo acíclico dirigido (DAG) de dependencias y reconcilie desviaciones (*drift*) automáticamente. Restricciones clave: el equipo domina Python, se dispone de 24 horas para tener el MVP operativo en Windows 11, y el diseño debe soportar abstracciones orientadas a objetos sin duplicar código entre los entornos `dev` y `prod`.

### 2. Alternativas
1. **Scripts Imperativos Mejorados (PowerShell + Docker CLI / Docker Compose):** Mantener la base de *DevForge v1.0* invocando comandos `docker network/run` o plantillas `docker-compose.yml` desde PowerShell.
   * *Ventajas:* Curva de aprendizaje nula; cero dependencias de motores IaC externos.
   * *Desventajas:* Ausencia de archivo de estado transaccional con bloqueo (*locking*) y sin capacidad nativa de *preview/diff* granular antes de aplicar cambios. No es portable a proveedores de nube pública (AWS/Azure) para las etapas E3/E4 ni soporta *Policy as Code*.
2. **Terraform / OpenTofu con HCL (HashiCorp Configuration Language):** Estándar de la industria basado en un lenguaje específico de dominio (DSL) declarativo.
   * *Ventajas:* Ecosistema masivo de proveedores, madurez comprobada en gestión de estado (`terraform.tfstate`) y detección de *drift*.
   * *Desventajas:* Obliga a aprender la sintaxis y limitaciones de HCL. La creación de abstracciones complejas, bucles condicionales dinámicos (como iterar sobre $N$ réplicas e inyectarlas dinámicamente en la configuración del balanceador) y pruebas unitarias resulta rígida y verbosa en comparación con un lenguaje de propósito general.
3. **Pulumi con Python (IaC Declarativa con Lenguaje de Propósito General):** Motor IaC moderno que construye un grafo de recursos declarativo utilizando el SDK de Python (`pulumi`).
   * *Ventajas:* Aprovecha el dominio existente de Python para aplicar Programación Orientada a Objetos real (`ComponentResource`), bucles nativos (`for`), tipado y manejo de estructuras de datos sin sacrificar el motor declarativo, el cálculo del DAG ni el archivo de estado transaccional. Soporta nativamente *Policy as Code* en Python (CrossGuard).
   * *Desventajas:* Introduce una capa adicional de ejecución (el runtime de Python comunicándose vía gRPC con el motor CLI de Pulumi) y requiere gestionar el entorno virtual (`venv`) junto con el binario de Pulumi.

### 3. Criterios de elección
* **Mantenibilidad mediante Abstracción Orientada a Objetos:** Capacidad del lenguaje para encapsular la topología completa (`Red + DB + N Réplicas + Proxy`) en una clase instanciable y parametrizable, evitando copiar y pegar bloques entre `dev` y `prod`.
* **Reconciliación de Estado e Idempotencia Nativa:** Existencia de un motor que persista el estado real en un JSON transaccional, calcule diferencias exactas (`preview`) y autorrepare recursos eliminados fuera de banda (*self-healing*).
* **Velocidad de Adopción (Time-to-Market < 24h):** Minimizar la fricción sintáctica aprovechando conocimientos previos en Python para cumplir con el plazo de la demo sin sacrificar rigor arquitectónico.
* **Extensibilidad hacia Nube y Gobernanza:** Capacidad de migrar de Docker a Azure/AWS y escribir reglas de seguridad como código usando el mismo lenguaje.

### 4. Decisión
Se elige **Pulumi utilizando Python 3** como motor y lenguaje de Infraestructura como Código para construir *DevForge Cloud*.

### 5. Sustento
* Contra **Mantenibilidad y Abstracción**: A diferencia de HCL en Terraform (donde los módulos son directorios estáticos sin herencia ni polimorfismo), Pulumi en Python permite heredar de `pulumi.ComponentResource`, facilitando la creación dinámica de $N$ réplicas de backend y la generación en memoria de la configuración del balanceador de carga con bucles estándar de Python.
* Contra **Reconciliación de Estado e Idempotencia**: Supera radicalmente a PowerShell/Docker Compose al mantener un archivo de estado con los IDs criptográficos e internos de cada recurso en Docker, permitiendo demostrar en vivo cómo el sistema detecta y repara la caída manual de un contenedor sin afectar la base de datos.
* Contra **Velocidad de Adopción y Extensibilidad**: Permite construir el MVP en horas usando un lenguaje conocido (Python) mientras se introduce una tecnología IaC de vanguardia que soporta más de 150 proveedores cloud y validación de políticas con CrossGuard.

### 6. Consecuencias y riesgos aceptados
* **Riesgo de mezclar lógica imperativa con estado declarativo:** Al usar Python completo, existe el riesgo de escribir código con efectos secundarios fuera del grafo de Pulumi (p. ej., llamadas directas al sistema de archivos durante el `preview`). *Mitigación:* Toda interacción con recursos dependerá exclusivamente de los constructores del SDK (`pulumi_docker`) y del manejo asíncrono de promesas (`Output.apply` / `Output.all`).
* **Dependencia del entorno Python local:** Si el `venv` se corrompe, el motor IaC no podrá evaluar el grafo. *Mitigación:* Se fijarán versiones exactas en `requirements.txt` gestionadas automáticamente por el runtime de Pulumi.
