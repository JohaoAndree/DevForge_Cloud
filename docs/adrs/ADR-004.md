## PARTE A — DECISIÓN (congelada al aceptar)

### 1. Contexto
Una vez operativa la arquitectura modular (`DevForgeEnvironment`) sobre el proveedor local de Docker (`ADR-001` a `ADR-003`), el sistema enfrenta tres retos para su madurez hacia entornos empresariales en las Etapas E3 y E4:
1. **Riesgo de violación de seguridad por error humano:** Aunque `config_loader.py` valida el YAML, un desarrollador podría modificar un componente o instanciar un contenedor adicional exponiendo el puerto `5432` de PostgreSQL al host público o montando `/var/run/docker.sock` en el grafo de Pulumi.
2. **Acoplamiento al proveedor de infraestructura local:** El componente actual instancia recursos `pulumi_docker`, pero el objetivo de portabilidad exige una estrategia clara para migrar a proveedores de nube pública (Azure for Students o AWS) sin reescribir el orquestador ni los contratos de configuración.
3. **Verificación manual propensa a omisiones:** Ejecutar `pytest` y validar los esquemas YAML manualmente antes de integrar cambios no garantiza calidad continua en un flujo colaborativo.

### 2. Alternativas
1. **Revisiones Manuales de Código (Pull Request Reviews) y Migración "Big Bang" del Código IaC:** Confiar en que el revisor humano detecte puertos expuestos en los PRs y, cuando se pase a la nube, reescribir `__main__.py` y `environment_stack.py` desde cero para Azure/AWS.
   * *Ventajas:* Cero código adicional de políticas o pipelines en el corto plazo.
   * *Desventajas:* Alta probabilidad de errores de seguridad en producción; reescribir todo el proyecto al cambiar de proveedor destruye la mantenibilidad y rompe los contratos existentes.
2. **Escáneres Externos de Archivos Estáticos (Checkov / tfsec) + Scripts Bash en CI:** Integrar herramientas externas pensadas para Terraform HCL o Kubernetes YAML en un pipeline genérico.
   * *Ventajas:* Herramientas conocidas en el ecosistema HCL.
   * *Desventajas:* Los analizadores estáticos de HCL no comprenden grafos dinámicos construidos en Python con Pulumi, por lo que no pueden evaluar en tiempo de pre-despliegue las propiedades resueltas de cada recurso `docker:index/container:Container`.
3. **Gobernanza Nativa con *Policy as Code* en Python (`policies/`), Contrato de Portabilidad Cloud (Patrón *Adapter/Translator* de Proveedor) y Pipeline GitOps en GitHub Actions:**
   * Implementar un módulo de políticas (`policies/security_policies.py` + `policies/PulumiPolicy.yaml`) que inspeccione la representación de los recursos del grafo de Pulumi y rechace obligatoriamente (`enforcement_level="mandatory"`) cualquier contenedor que exponga el puerto `5432` al host, monte `/var/run/docker.sock` o habilite PgAdmin en `prod`.
   * Definir el contrato inmutable de portabilidad cloud (`CloudTargetSpec` en `components/cloud_portability.py`) para mapear de forma determinista un `EnvironmentConfig` hacia sus equivalentes en nube pública (`azure` y `aws`).
   * Configurar un workflow declarativo de integración continua (`.github/workflows/iac-ci.yml`) que ejecute compilación, validación de manifiestos y `pytest` automáticamente en cada `push` o `pull_request`.

### 3. Criterios de elección
* **Cumplimiento de Seguridad Verificable en el Grafo (*Shift-Left Security*):** Capacidad de auditar programáticamente las propiedades de los recursos generados en Python antes o durante el despliegue y también dentro de `pytest`.
* **Trazabilidad de Portabilidad Multi-Nube:** Demostrar arquitectónicamente cómo un mismo `EnvironmentConfig` se traduce tanto a primitivos de contenedores locales (`docker`) como a una especificación de arquitectura cloud gestionada (`azure` / `aws`) sin alterar la entrada del usuario.
* **Automatización Reproducible sin Costo (GitOps Free Tier):** El pipeline de validación debe ejecutarse gratuitamente en GitHub Actions en menos de 60 segundos sin requerir credenciales bancarias activas ni dependencias adicionales en `requirements.txt`.

### 4. Decisión
Se elige implementar **Gobernanza como Código en Python (`policies/`)**, un **traductor determinista de portabilidad de arquitectura cloud (`components/cloud_portability.py`)** y un **pipeline GitOps automatizado en GitHub Actions (`.github/workflows/iac-ci.yml`)**.

### 5. Sustento
* Contra **Seguridad Verificable (*Shift-Left*)**: Las funciones validadoras puras en Python (`policies/security_policies.py`) permiten auditar cualquier diccionario de propiedades de un contenedor o configuración de entorno sin depender de demonios externos, asegurando que jamás se abra el puerto `5432` al exterior ni se monte `/var/run/docker.sock`.
* Contra **Portabilidad Multi-Nube**: Al desacoplar la especificación lógica (`EnvironmentConfig`) del proveedor mediante `translate_to_cloud_target(env_config, provider)`, se demuestra con código verificable cómo cada pieza del MVP local tiene su correspondencia exacta en servicios PaaS/CaaS de Azure (`azure-native`) y AWS (`aws`) para la Etapa E4.
* Contra **Automatización Reproducible sin Costo**: GitHub Actions ejecuta en cada commit la verificación sintáctica (`compileall`) y la suite completa de `pytest` con costo $0 y sin modificar `requirements.txt`.

### 6. Consecuencias y riesgos aceptados
* **Mantenimiento sincronizado de reglas de seguridad:** Si en el futuro se agrega un nuevo motor de base de datos (p. ej. Redis en puerto `6379`), la lista de puertos restringidos en `policies/security_policies.py` deberá actualizarse. *Mitigación:* Las reglas de puertos y volúmenes prohibidos se centralizan en constantes inmutables (`RESTRICTED_INTERNAL_PORTS` y `FORBIDDEN_HOST_PATHS`) cubiertas por pruebas unitarias.

## PARTE B — ESPECIFICACIÓN DE IMPLEMENTACIÓN (para el agente)

### 7. Alcance y fuera de alcance
* **Incluye:**
  * Creación del paquete de gobernanza `policies/` (`policies/__init__.py`, `policies/PulumiPolicy.yaml`, `policies/security_policies.py`) con validadores puros de *Policy as Code* sin agregar nuevas librerías a `requirements.txt`.
  * Creación del módulo de portabilidad multi-nube `components/cloud_portability.py` con el contrato inmutable `CloudTargetSpec` y la función `translate_to_cloud_target`.
  * Creación del pipeline GitOps de integración continua en `.github/workflows/iac-ci.yml`.
  * Creación de la suite de pruebas `tests/test_governance_and_portability.py` validando las reglas de seguridad, la traducción a proveedores cloud (`azure` y `aws`) y la validez estructural del workflow CI.
* **NO incluye:**
  * Modificación de `requirements.txt`, `__main__.py` o de los tests de ADRs previos (`test_project_bootstrap.py`, `test_stack_isolation.py`, `test_environment_stack.py`).
  * Despliegue real contra suscripciones activas de Azure o AWS durante la ejecución de `pytest`.

### 8. Pasos de implementación

1. **Paso 1 — Motor de Gobernanza y *Policy as Code* (`policies/`):**
   * **Archivos:** `policies/__init__.py`, `policies/PulumiPolicy.yaml`, `policies/security_policies.py`
   * **Cambios / Firmas:**
     * Crear `policies/__init__.py` con docstring de módulo en español sin tildes.
     * Crear `policies/PulumiPolicy.yaml` con las claves exactas:
       * `runtime: python`
       * `description: Politicas de seguridad y gobernanza para DevForge Cloud`
     * Crear `policies/security_policies.py` definiendo:
       * Constantes inmutables:
         * `RESTRICTED_INTERNAL_PORTS: tuple[int, ...] = (5432,)`
         * `FORBIDDEN_HOST_PATHS: tuple[str, ...] = ("/var/run/docker.sock", "//./pipe/docker_engine")`
       * Clase inmutable `@dataclass(frozen=True) class PolicyViolation:` con atributos `policy_name: str`, `resource_name: str`, `message: str` y `enforcement_level: str = "mandatory"`.
       * Función pública `validate_container_security(resource_name: str, container_props: dict[str, object], stack_environment: str) -> tuple[PolicyViolation, ...]` que inspeccione un diccionario de propiedades de contenedor y retorne una tupla ordenada de `PolicyViolation` (vacía si cumple todo) bajo estas tres reglas:
         1. `"no-public-database-port"`: si en `container_props.get("ports", [])` (lista de dicts con clave `"internal"` y `"external"`) algún elemento tiene `"internal"` dentro de `RESTRICTED_INTERNAL_PORTS` y define `"external"` no nulo.
         2. `"no-docker-socket-mount"`: si en `container_props.get("volumes", [])` o `container_props.get("mounts", [])` (lista de dicts) algún valor de `"host_path"`, `"source"` o `"volume_name"` contiene alguna ruta de `FORBIDDEN_HOST_PATHS`.
         3. `"no-pgadmin-in-prod"`: si `stack_environment == "prod"` y `str(container_props.get("image", ""))` contiene `"pgadmin"`.
   * **Verificación del paso:** Ejecutar `venv\Scripts\python -m compileall -q policies` con código de salida `0`.

2. **Paso 2 — Traductor de Portabilidad Multi-Nube (`components/cloud_portability.py`):**
   * **Archivos:** `components/cloud_portability.py`
   * **Cambios / Firmas:**
     * Definir las constantes de proveedores soportados: `SUPPORTED_CLOUD_PROVIDERS: tuple[str, ...] = ("azure", "aws")`.
     * Definir `@dataclass(frozen=True) class CloudTargetSpec:` con los atributos:
       * `provider: str`
       * `stack_name: str`
       * `network_service: str`
       * `compute_service: str`
       * `database_service: str`
       * `load_balancer_service: str`
       * `target_replicas: int`
       * `expose_admin_ui: bool`
       * `resource_group_or_vpc_name: str`
     * Implementar en `CloudTargetSpec` el método público `to_dict(self) -> dict[str, str | int | bool]` que retorne un diccionario nuevo con todos sus campos.
     * Implementar la función pública `translate_to_cloud_target(env_config: EnvironmentConfig, provider: str) -> CloudTargetSpec` que:
       * Normalice `normalized_provider = provider.strip().lower()`.
       * Lance `ValueError` si `normalized_provider not in SUPPORTED_CLOUD_PROVIDERS`.
       * Para `"azure"`, retorne `CloudTargetSpec` con `network_service="azure-native:network:VirtualNetwork"`, `compute_service="azure-native:app:ContainerApp"`, `database_service="azure-native:dbforpostgresql:FlexibleServer"`, `load_balancer_service="azure-native:app:ManagedEnvironmentLoadBalancer"`, `target_replicas=env_config.replicas`, `expose_admin_ui=env_config.enable_pgadmin`, y `resource_group_or_vpc_name=f"rg-devforge-{env_config.stack_name}"`.
       * Para `"aws"`, retorne `CloudTargetSpec` con `network_service="aws:ec2:Vpc"`, `compute_service="aws:ecs:FargateService"`, `database_service="aws:rds:Instance"`, `load_balancer_service="aws:lb:LoadBalancer"`, `target_replicas=env_config.replicas`, `expose_admin_ui=env_config.enable_pgadmin`, y `resource_group_or_vpc_name=f"vpc-devforge-{env_config.stack_name}"`.
   * **Verificación del paso:** Ejecutar `venv\Scripts\python -m compileall -q components policies` con código de salida `0`.

3. **Paso 3 — Pipeline GitOps de Integración Continua en GitHub Actions:**
   * **Archivos:** `.github/workflows/iac-ci.yml`
   * **Cambios / Firmas:**
     * Crear `.github/workflows/iac-ci.yml` con formato YAML válido que defina:
       * `name: DevForge Cloud IaC CI`
       * Disparadores `on:` para `push` (ramas `["main"]`) y `pull_request` (ramas `["main"]`).
       * Un job `validate-and-test` sobre `runs-on: ubuntu-latest` con pasos para: checkout del repositorio (`actions/checkout@v4`), configuración de Python `3.11` (`actions/setup-python@v5`), instalación de dependencias (`python -m pip install -r requirements.txt`), verificación sintáctica (`python -m compileall -q .`) y ejecución de pruebas unitarias y de gobernanza (`python -m pytest`).
   * **Verificación del paso:** Validar el YAML ejecutando `venv\Scripts\python -c "import yaml; yaml.safe_load(open('.github/workflows/iac-ci.yml'))"` con código de salida `0`.

4. **Paso 4 — Pruebas unitarias de Gobernanza (*Policy as Code*), Portabilidad y CI:**
   * **Archivos:** `tests/test_governance_and_portability.py`
   * **Cambios / Firmas:**
     * Crear `tests/test_governance_and_portability.py` con las siguientes pruebas:
       * `test_validate_container_security_allows_compliant_prod_containers()`: verifica que un contenedor PostgreSQL sin puertos expuestos (`ports=[]`) y un contenedor `whoami` en `"prod"` producen `0` violaciones (`()`).
       * `test_validate_container_security_blocks_exposed_postgres_socket_and_prod_pgadmin()`: verifica que `validate_container_security` detecta y retorna las violaciones `"no-public-database-port"` (cuando `ports=[{"internal": 5432, "external": 5432}]`), `"no-docker-socket-mount"` (cuando se monta `"/var/run/docker.sock"`) y `"no-pgadmin-in-prod"` (cuando se usa `"dpage/pgadmin4:latest"` en `"prod"`).
       * `test_translate_to_cloud_target_maps_azure_and_aws_specifications()`: verifica que `translate_to_cloud_target` mapea correctamente un `EnvironmentConfig` de `prod` (`replicas=3`, `enable_pgadmin=False`) hacia `"azure"` y `"aws"`, y lanza `ValueError` ante un proveedor desconocido (p. ej. `"heroku"`).
       * `test_github_actions_workflow_declares_compile_and_pytest_steps()`: carga `.github/workflows/iac-ci.yml` con `yaml.safe_load`, verifica que existe el job `validate-and-test` y que sus pasos incluyen `compileall` y `pytest`.
   * **Verificación del paso:** Ejecutar `venv\Scripts\python -m pytest` y confirmar que todas las suites del proyecto (`ADR-001` a `ADR-004`) pasan en verde (`exit code 0`).

### 9. Criterios de aceptación
1. Existe `policies/PulumiPolicy.yaml` y `policies/security_policies.py` detecta de forma determinista las violaciones `"no-public-database-port"`, `"no-docker-socket-mount"` y `"no-pgadmin-in-prod"`.
2. `components/cloud_portability.py` define `CloudTargetSpec` como `@dataclass(frozen=True)` y traduce `EnvironmentConfig` hacia `"azure"` y `"aws"` sin efectos secundarios, rechazando proveedores no soportados con `ValueError`.
3. Existe `.github/workflows/iac-ci.yml` con sintaxis YAML válida ejecutando `compileall` y `pytest`.
4. `venv\Scripts\python -m pytest` ejecuta todas las pruebas de `ADR-001`, `ADR-002`, `ADR-003` y `ADR-004` y finaliza con código de salida `0`.
